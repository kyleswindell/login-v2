## 1. Purpose

Keep comments useful, current, and intentional.

Comments should explain rationale, constraints, contracts, and non-obvious behavior. They should not repeat code.

---

## 2. Source

This standard is informed by:

- [Modern Commenting Standards Research](../../09-reference/documentation/Modern%20Commenting%20Standards%20Research.md)

---

## 3. Core Rule

Write code so names, types, structure, tests, and file ownership explain the normal path.

Use comments only when the code cannot clearly communicate:

- intent
- constraints
- security rationale
- data boundary rationale
- compatibility rationale
- public contract expectations
- non-obvious operational behavior

If a line feels like it needs a comment, first consider whether a clearer method name, variable name, enum, value object, form request, service extraction, test name, or document link would remove the need.

---

## 4. Good Comments Explain

Use comments when the reader needs context that is not obvious from the code.

Good comments explain:

- why a security, tenant, workspace, permission, or data boundary is enforced in a specific way
- why an implementation intentionally differs from a Laravel default
- why an operation is fail-open or fail-closed
- why logging intentionally captures or omits a field
- why retry, idempotency, locking, caching, or queue behavior has a specific constraint
- why a temporary compatibility path exists
- what contract a public service method expects when types alone are not enough
- why a UI component intentionally differs from the upstream reference
- why a migration, backfill, or data correction is intentionally conservative

---

## 5. Avoid Comment Noise

Do not add comments that only repeat code.

Avoid:

```php
// Get the user.
$user = Auth::user();
```

Do not leave:

* commented-out examples
* starter code
* old implementations
* unused imports
* abandoned debug notes
* temporary investigation comments
* changelog comments inside source files

Git history owns removed code.

---

## 6. File Headers

### 6.1. PHP Source Files

Do not add broad file headers to PHP source files by default.

PHP file-level comments are allowed only when they orient the reader to a file-wide boundary that is not obvious from namespace, class name, interface name, or surrounding folder.

If licensing headers are needed later, prefer short SPDX identifiers over long boilerplate.

### 6.2. Blade, CSS, And JavaScript UI Files

Blade, CSS, and JavaScript files that are part of the shared UI/component system may require project-standard file/header comments.

Use file/header comments for UI files when they identify:

* file path
* component or pattern owner
* purpose
* public contract or expected pairing with Blade/CSS/JS
* relationship to UI reference, contract, or token files

Keep those headers short and consistent.

### 6.3. Markdown Documentation Files

Markdown documentation files must use the `DOC-META` header block when new or materially rewritten.

Do not add author, creation date, last modified, or changelog comments. Git owns authorship and history.

---

## 7. PHPDoc

Use PHPDoc when it improves public contracts, static analysis, generic types, array shapes, or framework integration.

Good PHPDoc examples:

```php
/**
 * @param array<string, mixed> $metadata
 */
public function recordEvent(string $event, array $metadata = []): void
```

```php
/**
 * @return array<string, string>
 */
protected function casts(): array
```

Avoid PHPDoc that only repeats method names, typed parameters, or return types.

Avoid:

```php
/**
 * Register any application services.
 */
public function register(): void
```

Use PHPDoc for:

* array shapes
* collection item types
* generic template types
* magic framework methods when needed
* public service contracts that cannot be fully expressed through native types
* intentional exceptions to normal behavior

Do not use PHPDoc as a substitute for clear names or proper types.

---

## 8. Inline And Block Comments

Use inline comments sparingly.

Prefer a short block comment above the affected block when the explanation applies to multiple lines.

Inline comments are acceptable for short local rationale:

```php
// Keep audit logging fail-safe so auth flows are not blocked by telemetry outages.
```

Avoid end-of-line comments unless the comment is brief and clearly improves a dense line.

If a line needs a long end-of-line comment, split the code or extract a named value.

---

## 9. TODO And FIXME

Use TODO only when there is durable context and a clear removal path.

Preferred format:

```php
// TODO: https://github.com/kyleswindell/login-v2/issues/123 - Remove fallback after tenant resolver rollout.
```

If an issue does not exist yet, link to a canonical doc or decision:

```php
// TODO: docs/03-architecture/platform-boundary.md - Replace temporary bootstrap after shell migration.
```

Avoid person-only TODOs:

```php
// TODO: Kyle fix this.
```

Do not use FIXME as a separate severity system for now. Use an issue-linked TODO and track severity in the issue or planning document.

---

## 10. Tests

Prefer descriptive test method names over comments.

Comment tests only when setup is intentionally unusual, protects a regression, or documents a non-obvious security, tenant, workspace, data, or UI boundary.

Do not comment the basic arrange / act / assert flow.

Good test comments explain why the test setup is strange, not what each assertion does.

---

## 11. Config And Docs

Configuration comments should be short and close to the setting only when they clarify constraints.

Long explanations belong in `docs/`.

JSON does not support comments. Use adjacent Markdown documentation for JSON-based configuration.

Do not store secrets, credentials, tokens, or sensitive environment details in comments or docs.

---

## 12. Comments Generated By Stubs

Repository stubs may include required comments and file headers when those comments are part of the approved file archetype.

Generated comments must follow the same rules as manually written comments:

- they must remain accurate after generation
- they must explain durable intent or constraints
- they must not repeat obvious syntax
- they must not retain placeholder instructions in completed source files
- they must be removed when they do not apply
- they must be updated when ownership or behavior changes

---

### 12.1. PHP Files

Do not generate broad file headers for ordinary PHP classes, migrations, factories, seeders, or tests by default.

Use PHPDoc only when it expresses information not adequately represented by native types or code structure.

---

### 12.2. Blade, CSS, And UI JavaScript Files

UI stubs may generate the repository-required file header.

These headers may identify:

- file path
- purpose
- component or behavior owner
- related implementation files
- stable implementation constraints

Do not include authors, creation dates, modified dates, or embedded changelogs.

The presence of a generated header does not excuse stale or inaccurate documentation.

---

## 13. Maintenance Rule

When code changes, update or delete related comments in the same change.

A stale comment is worse than no comment.

During refactors, comments must be reviewed as part of the moved code, not blindly carried forward.
