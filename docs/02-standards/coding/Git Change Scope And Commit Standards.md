# Git Change Scope And Commit Standards

Parent: [Coding Standards Index](index.md)

## 1. Purpose

Define durable Git change-scope and commit rules independent of the deprecated batch workflow.

## 2. Core Rule

One commit should represent one issue or tightly coupled concern.

A commit must be:

- scoped
- intentional
- reviewable
- verified
- free of unrelated files

## 3. Working-Tree Inspection

Before editing or staging, inspect:

    git status --short --branch

Before committing, inspect:

    git status --short
    git diff
    git diff --staged

Identify:

- current branch
- staged files
- unstaged files
- untracked files
- unrelated work
- another session's changes

Do not reset or discard changes you do not own.

## 4. Explicit Staging

Stage explicit paths.

Do not use:

    git add .

in a dirty working tree.

Do not stage:

- unrelated cleanup
- generated output not required by the issue
- local environment files
- secrets
- another session's files
- speculative follow-up work

## 5. Commit Scope

A commit should map to:

- one GitHub issue
- one implementation slice
- one documentation cleanup concern
- one migration concern
- one review fix concern

Split commits when changes can be reviewed or reverted independently.

Keep implementation and required documentation synchronization in the same work cycle.

## 6. Commit Timing

Commit when the work is:

- complete for the chosen scope
- syntactically valid
- tested as required
- documented
- reviewable
- free of known blocking defects

Local manual review may inspect uncommitted changes.

Accepted work should be committed before it is treated as durable review evidence.

## 7. Commit Messages

Use a concise imperative summary.

The message should identify the concern, not the workflow ceremony.

Examples:

    Add planning and decision documentation standards
    Replace deprecated batch runbooks
    Fix notification service restart verification

Avoid:

- vague messages
- status-only messages
- autogenerated noise
- multiple unrelated concerns

## 8. Verification

Before committing:

- run issue-required checks
- run targeted tests
- run formatting or syntax checks
- inspect generated output
- inspect documentation links when applicable
- review the final diff

Record checks in the issue, PR, or work summary.

## 9. Push

Push only when:

- the task authorizes it
- the branch is appropriate
- the commit is reviewable
- remote synchronization is required
- no secrets or local-only artifacts are included

Fetch before pushing when another device or contributor may have updated the branch.

Do not force-push shared branches without explicit authorization.

## 10. Shared Files

Serialize updates to:

- indexes
- identifier registries
- planning matrices
- shared configuration
- migration sequences
- release files
- shared staging state

Re-read the current branch version before finalizing shared files.

## 11. Parallel Work

Concurrent writers require separate branches and worktrees.

Use:

- [Agent Session Concurrency And Worktree Standards](../coding-agents/Agent%20Session%20Concurrency%20And%20Worktree%20Standards.md)
- [Parallel Worktree Setup](../../10-runbooks/parallel-worktree-setup.md)

## 12. Prohibited Practices

Do not:

- mix unrelated cleanup
- commit secrets
- commit local environment files
- hide failing verification
- amend another contributor's published commit without approval
- overwrite uncommitted work
- use deprecated batch IDs as required commit structure
- create artificial checkpoint commits with no reviewable value

## 13. Stop Conditions

Stop before committing when:

- scope cannot be described clearly
- staged files include unrelated work
- verification fails
- ownership is unclear
- another writer may own the files
- the branch is wrong
- sensitive content is present
- required documentation is incomplete
- a destructive migration lacks approval
