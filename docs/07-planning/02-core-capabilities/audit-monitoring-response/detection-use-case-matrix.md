# Detection Use Case Matrix

Status: Planning matrix

## Purpose

Track planned detection use cases that convert high-risk threats into audit/monitoring signals, notifications, response playbooks, and tests.

This matrix sits beside the [Threat-Control Traceability Matrix](threat-control-traceability-matrix.md). It does not replace threat modeling, audit contracts, monitoring implementation, notification type declarations, runbooks, or tests.

## Matrix Columns

| Column | Meaning |
| --- | --- |
| Detection ID | Stable detection use case key. |
| Threat | Threat or abuse case being detected. |
| Source Events | Audit, monitoring, job, health, or domain events consumed. |
| Signal Rule | Window, threshold, grouping, or trigger rule. |
| Severity | Info, low, medium, high, or critical. |
| Affected Core Owner | Owner of evidence, detection, or domain action. |
| Required Audit Evidence | Minimum safe fields needed for investigation. |
| Notification Type | Planned persistent notification type key. |
| Response Playbook | Runbook/playbook key. |
| Automated Response Allowed | Safe automated response, if any. |
| Manual Response Required | Human review or approval requirement. |
| Tests | Required test coverage. |
| Status | Planned, implemented, tested, failing, accepted-risk, deferred, or not-applicable. |

## Maintenance Rules

- Add detection rows before implementing new high-risk threat monitoring.
- Keep detection IDs stable once referenced by tests, notification types, runbooks, or code.
- Do not add noisy detections without threshold, severity, owner, and tuning notes.
- Do not mark a detection tested until it can generate a signal and required notification/runbook mapping is verified.
- Keep containment actions owned by Auth, Identity, Access, DataProtection, Secrets, or Vulnerability Management.
- Keep this matrix in planning until standards, runbooks, and implementation batches promote specific rules.
