# Threat-Control Traceability Matrix

Status: Planning matrix

## Purpose

Track initial security threats and map them to controls, tests, audit events, monitoring signals, notifications, runbooks, and owners.

This matrix is a planning artifact. It does not replace standards, feature behavior, schema contracts, code, tests, or runbooks.

Threats that require operational detection should also be represented in the [Detection Use Case Matrix](detection-use-case-matrix.md).

## Matrix Columns

| Column | Meaning |
| --- | --- |
| Threat ID | Stable planning ID. |
| Threat | Abuse case or failure mode. |
| Affected Capability | Core capability or business module. |
| Affected Data | Data assets or sensitive records involved. |
| Entry Point | Route, command, job, webhook, UI, import, or integration entry point. |
| Trust Boundary | Boundary crossed by request, actor, or data. |
| Risk | Planning risk level. |
| Preventive Controls | Controls intended to block or reduce the threat. |
| Detective Controls | Controls intended to detect the threat or failure. |
| Corrective Controls | Controls intended to contain, recover, or remediate. |
| Enforced By | Middleware, policy, service, job, release gate, or runbook owner. |
| Tests | Required test categories. |
| Audit Events | Required accountable evidence. |
| Monitoring Signals | Required operational or security signals. |
| Notifications | Required user/operator notifications. |
| Runbook | Response procedure when the threat materializes. |
| Status | Planned, implemented, tested, failing, accepted-risk, deferred, or not-applicable. |
| Owner | Owning Core capability, Module, UI, Laravel integration, or operations owner; Surface, Delivery Adapter, and Registry remain technical responsibilities beneath that owner. |

## Control Status Labels

| Status | Meaning |
| --- | --- |
| Planned | Direction is accepted in planning but not implemented. |
| Implemented | Control exists in code/config/docs but test/evidence status is not complete. |
| Tested | Automated or manual evidence exists and passes. |
| Failing | Evidence exists and fails. |
| Accepted-risk | Risk is formally accepted with owner, reason, and expiration. |
| Deferred | Not needed for current maturity or blocked by predecessor work. |
| Not-applicable | Threat/control does not apply to this surface. |

## Maintenance Rules

- Add new threat rows before implementing high-risk Auth, Identity, Access, DataProtection, Security, Audit, Monitoring, Notifications, Secrets, or Vulnerability Management work.
- Keep threat IDs stable once referenced by tests, standards, runbooks, or code comments.
- Link controls to real tests and evidence before marking them tested.
- Link high-risk threats to detection use cases unless detection is explicitly not applicable.
- Keep domain-specific semantics with the owning capability or business module.
- Do not use this matrix as a replacement for standards, runbooks, database contracts, or implementation tickets.
