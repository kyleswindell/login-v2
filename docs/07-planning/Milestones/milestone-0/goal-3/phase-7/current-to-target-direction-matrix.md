# Phase 7 Current-To-Target Direction Matrix

Parent: [Phase 7.2 Current-To-Target Placement Mappings](7-2-current-to-target-placement-mappings.md)

## 1. Purpose

Record the accepted pattern-level migration direction from the current repository structure to the Goal 3 target architecture.

This matrix does not authorize physical migration, deletion, compatibility implementation, schema changes, or file-by-file movement.

## 2. Matrix Rules

* Current placement is evidence, not target authority.
* Current non-UI implementation is disposable by default.
* Accepted UI public contracts remain protected.
* Compatibility is not required unless separately entered in the compatibility register.
* Each row uses one primary disposition: `Retain`, `Move`, `Rename`, `Split`, `Merge`, `Extract`, `Replace`, `Remove later`, or `Decision blocked`.
* Follow-on rewriting, relocation, or cleanup treatment belongs in `Notes`, not in a combined disposition value.
* `Retain` preserves the owner or structural role; it does not require preserving the current implementation unchanged.
* `Remove later` requires a separately accepted cleanup issue.
* Mapping IDs are stable. Later additions remain in the applicable subject section rather than forcing renumbering.
* Later owners may refine internal design without reopening the accepted Goal 3 ownership or placement direction.

## 11. Compatibility Position

No compatibility obligation is created by this matrix for:

* `App\Platform\` namespaces;
* `App\Modules\` namespaces;
* current internal class names;
* `/platform/*` routes;
* a proposed `/admin/*` route family;
* current command names;
* current configuration keys;
* current manifest formats;
* current Platform, Surface, or false Module paths;
* current non-UI test structure.

Any required compatibility must be entered separately in `compatibility-register.md` with concrete evidence.
