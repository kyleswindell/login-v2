## 1. Purpose

Provide one quick-review location for the overall core service build plan, target folders/files, configuration notes, sequencing, and source planning docs.

This matrix tracks implementation ownership and sequencing. It does not replace source planning docs, architecture contracts, feature behavior contracts, schema contracts, standards, or runbooks. Canonical behavior, schema, security requirements, and operational procedures must still be promoted into their owning source docs before implementation.

[ADR-0006: Tenant, Instance, Workspace, Principal, Actor, And Invocation Vocabulary](../01-decisions/adr-0006-tenant-instance-workspace-principal-and-invocation-vocabulary.md) defines the canonical isolation, identity, assurance, event-attribution, and invocation terms.

This matrix records planning application and does not redefine that contract.

### Ownership

| Owner | Meaning | Current Or Target Direction |
| --- | --- | --- |
| Core | Required base-application behavior, state, coordination, infrastructure, and contracts that must operate without optional Modules. | Current and target Core paths are reconciled through Goals 02, 03, and 09. |
| Modules | Optional, cohesive feature sets delivered as independently versioned, installable, and distributable Composer packages. | `Modules/{Module}` during current development; final package and repository topology is owned by Goal 03. |
| UI | Reusable Elements, Components, Patterns, Layouts, CSS, JavaScript, icons, contracts, tests, and review evidence. | Primarily `resources/views/components`, `resources/css`, and `resources/js`; ownership follows responsibility rather than path. |

### Tenant And Runtime Scope

```text
Tenant
└── exclusively owns one Instance
    └── owns User Accounts
        └── each authenticated Account receives a resolved Workspace
```

- One Tenant owns one Instance.
- Instance is the logical isolation boundary.
- Workspace is resolved per authenticated User Account and is not a stored container or database boundary.
- The Internal Tenant follows the same model as clients.
- Global Administration is an authorized Surface within Internal Tenant Workspaces.

### Principal And Assurance

```text
Principal Identity
├── Human Principal
│   └── User Account
│       └── User Identity
└── Non-Human Principal
    └── Non-Human Identity
        ├── Service Account
        ├── Workload Identity
        └── Application Principal

Request Assurance Context
├── Machine Identity
├── Network Identity
└── Network Context
```

- User Accounts and User Identity records belong to one Tenant Instance.
- There is no canonical global or implicit cross-Tenant User Identity.
- Machine Identity is independent from NHI.
- Network Identity is verified identity; Network Context is observed transport and risk evidence.

### Actor And Invocation

Actor attribution includes the Principal and applicable Machine Identity, Network Identity, and Network Context.

Canonical Invocation Channels:

- `interactive_web`
- `api_request`
- `webhook_request`
- `console_command`
- `queued_job`
- `event_consumer`
- `scheduled_task`
- `internal_system`

Jobs, commands, APIs, webhooks, events, and schedulers are execution mechanisms, not Principal or Actor types.

### Accepted Compatibility Rules

- `Platform` is retired as a peer source-of-truth owner.
- `App Instance` is a transitional descriptive alias for Instance.
- `tenant_workspace`, `internal_workspace`, and separate control-plane Workspace models are superseded.
- bare `Identity` should be qualified.
- `Service Identity` as the umbrella is replaced by Non-Human Identity.
- Workspace must not be used as persistent data scope.
- source IP alone is not Machine Identity or Network Identity.

## 14. Dashboard And UI Deferral Rules

- Do not build DataProtection dashboards before classification, data asset, export, and retention enforcement exists.
- Do not build DataGovernance dashboards before governance registry definitions, owner/steward workflows, privacy request workflows, and retention review paths exist.
- Do not build DLP dashboards before data classification, export/download enforcement, audit events, and monitoring signals exist.
- Do not build Offensive Testing dashboards before Vulnerability Management can own findings, private evidence handling exists, and retest workflow is real.
- Do not build Secrets dashboards before redaction, inventory, storage rules, release checks, and Auth hardening have a baseline.
- Do not build Supply Chain dashboards before dependency inventory, SBOM files, build artifact evidence, and release gates exist.
- Do not build Vulnerability dashboards before finding sources, owners, SLAs, release gates, and accepted-risk rules exist.
- Do not build Security dashboards before route tiers, redaction, header checks, and release checks produce evidence.
- Do not build Security control dashboards before threat-control mappings, tests, audit events, monitoring signals, notifications, and runbook evidence exist.
- Do not build detection signals or security case dashboards before real detection rules, notifications, runbook links, and evidence queries exist.
- Do not build deployment readiness dashboards before checks, deployment evidence, backup/rollback evidence, and public exposure/storage checks exist.
- Do not build service account, API token, webhook, or API activity admin views before token hashing, access policies, webhook verification, audit events, and monitoring signals exist.
- Do not build forensics dashboards before request correlation, audit/monitoring evidence fields, private evidence export, redaction, retention, and runbooks exist.
- Do not build universal renderers for normal CRUD/detail/form/business pages; use thin URL views, ViewModels, and purpose-built patterns.
- Do not build renderer-driven surfaces before the backing registry or contribution definitions exist.
- Do not use Security Checklist as the enforcement owner.
- Admin UI should display evidence from real enforcement/check systems, not become the system itself.

## 16. Accepted Key Conventions

The following planning applications are accepted under ADR-0007. Canonical grammar, family uniqueness, collision behavior, and compatibility rules remain owned by the linked standard.

| Area                  | Recommendation                                                                                                                                                                        | Reason                                                                                                                             |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Identity/Users        | owner key `identity`; permission namespace `users.*`; visible label `Users`                                                                                                           | Identity owns lifecycle/account state; Users is the admin-facing surface and permission vocabulary.                                |
| Access Control        | owner key `access`; permission namespace `access.*`; visible label `Access Control`                                                                                                   | Shorter permission keys and a broader capability name than `access-control.*`.                                                     |
| Roles                 | physical owner eventually under `app/Core/Access`; permission namespace remains `roles.*`                                                                                             | Roles are an Access child surface but keep role-specific action vocabulary.                                                        |
| Data Governance       | owner key `data_governance`; capability-first permission namespaces use snake-case segments such as `data_governance.*`; visible label `Data governance` only for approved admin surfaces | Governance owns policy, purpose, privacy rights, stewardship, and data quality; DataProtection enforces controls.                  |
| DLP / Exfiltration    | owner key `data_protection`; event and detection namespace `security.dlp.*`                                                                                                           | DLP policy is DataProtection-owned; exfiltration signals are Monitoring-owned.                                                     |
| Digital Forensics     | owner key `audit`; permission namespace `forensics.*`; event namespace `security.forensics.*`                                                                                         | Forensic evidence is Audit-owned, with Monitoring, Security, DataProtection, Access, Notifications, and Incident Response support. |
| Secrets Management    | physical owner under `app/Core/Security/Secrets`; permission namespace `secrets.*`; visible label `Secrets` only for approved admin surfaces                                          | Secrets are security-owned credential handling, not a business module or DataProtection dashboard.                                 |
| Software Supply Chain | owner key `supply_chain`; event/detection namespace `security.supply_chain.*`; visible label `Supply chain` only under Security admin surfaces                                        | Supply chain is a security subcapability for dependencies, SBOMs, artifacts, and release evidence, not a business module.          |
| Offensive Testing     | owner key `offensive_testing`; event/detection namespace `security.offensive.*`; visible label `Offensive testing` only under approved Security admin surfaces                        | Offensive testing is controlled security validation and evidence, not exploit tooling or a business module.                        |
| Notifications         | owner key `notifications`; permission namespace `notifications.*`                                                                                                                     | Delivery/inbox state is its own core capability.                                                                                   |
